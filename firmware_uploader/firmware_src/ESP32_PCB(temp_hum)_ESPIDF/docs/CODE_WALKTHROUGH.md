# Обяснение на кода на AgroMonitor (ESP-IDF прошивка)

Подробно ръководство по собствения код на проекта `ESP32_PCB(temp_hum)_ESPIDF`, написано за човек, който за първи път среща ESP-IDF и FreeRTOS. Подредено е **от хардуера нагоре към логиката**, а накрая има обзор как всичко се свързва.

| | |
|---|---|
| Обхват | 66 файла `.cpp` и `.h`, около 5 000 реда собствен код |
| Платформа | ESP32-S3, ESP-IDF 5.3–5.5, FreeRTOS, радио чип SX1262 през RadioLib |
| Устройства | `sensor`, `repeater`, `executor`, `gateway`, `executor_wifi`, `config` |
| Състояние | Проверен само в симулатор на PC. **Не е компилиран с истински ESP-IDF и не е пускан на хардуер.** |

## Как да четеш този документ

* Всеки файл е в таблица `Код` / `Обяснение`. Където файлът е по-дълъг, има и колона `Ред` с номера на реда във файла.
* Първо се чете `.h` файлът (договорът: какво предлага модулът), после `.cpp` (как го прави).
* Разделите са подредени така, че всеки ползва само вече прочетени: хардуер → данни и сигурност → радио → JSON и конфигурация → gateway → мрежа и sensor → repeater и executor → executor_wifi.
* Накрая (глава 10) има обзор: слоеве, устройства, път на пакета и таблица "кой кого вика".

**Не са описани ред по ред:** `CMakeLists.txt`, `sdkconfig.defaults` и `idf_component.yml` файловете (освен тези на `agro_board`, `agro_hal` и `agro_core`), както и `README.md` на проекта.

## Речник

| Понятие | Какво е |
|---|---|
| **ESP-IDF** | Официалният SDK на Espressif за ESP32. Дава драйвери (GPIO, SPI, I²C, Wi-Fi), библиотеки (NVS, mbedTLS, MQTT) и билд система (`idf.py`, CMake). |
| **FreeRTOS** | Малка операционна система вътре в ESP-IDF. Позволява няколко "задачи", които изглеждат като да работят едновременно. |
| **Компонент** | Папка с `CMakeLists.txt`, която казва кои файлове да се компилират и от какво зависи (`REQUIRES`). |
| **`app_main`** | Входната точка на приложението (като `setup()` в Arduino). Изпълнява се като една задача. |
| **Задача (task)** | Функция с безкраен цикъл и собствен стек. Планировчикът (scheduler) превключва между задачите. |
| **Приоритет** | По-голямото число печели. Готова задача с по-висок приоритет изпреварва по-нисък. |
| **Стек** | Памет за локалните променливи на задачата. В IDF размерът се задава в **байтове**. Малък стек води до срив. |
| **Опашка (queue)** | Безопасен канал между задачи. Елементите се **копират** в нея. Затова между задачите няма споделени променливи. |
| **Известие (notification)** | Лек сигнал към една задача. `ulTaskNotifyTake` блокира, докато някой я "бутне". Много известия се свиват в едно събуждане. |
| **ISR** | Функция, която хардуерът вика при прекъсване. Трябва да е много кратка и да не блокира. Тук само "бута" задача. |
| **`IRAM_ATTR`** | Слага функцията във вътрешна бърза RAM, за да работи и когато флашът е зает. |
| **Mutex** | Ключ за споделен ресурс. Само една задача го държи наведнъж. Нужен е, когато две задачи пипат едно и също нещо. |
| **Tick** | Прекъсване на всеки 1 ms (`CONFIG_FREERTOS_HZ=1000`), по което планировчикът решава кога да превключи. |
| **`esp_timer`** | Таймер с микросекундна точност, който вика функция след определено време. |
| **NVS** | Малка "база данни" ключ → стойност във флаша. Оцелява при рестарт. Тук пази настройките. |
| **`sdkconfig`** | Настройките на системата. `sdkconfig.defaults` ги задава за всяко приложение. |
| **RTC памет** | Памет, която оцелява при **дълбок сън** (не и при изключване на тока). `RTC_DATA_ATTR` слага променлива там. |
| **Лек сън (light sleep)** | Процесорът спира, RAM се пази, продължава от същото място. |
| **Дълбок сън (deep sleep)** | Почти всичко се изключва, RAM се губи, при събуждане `app_main` започва отначало. |
| **Watchdog** | Таймер, който рестартира чипа, ако задачите зациклят. |
| **LoRa** | Дълъг обхват, ниска скорост. **SF** (7–12) е "бавността" на модулацията, **BW** е ширината на канала. |
| **CAD** | Channel Activity Detection: "слуша ли някой на канала?" Нужно е преди предаване. |
| **DIO1** | Пин на радиото, който се вдига при събитие (пакет получен, предаване готово). |
| **MQTT** | Протокол "публикувай и се абонирай" през брокер. Gateway-ът публикува измервания и се абонира за команди. |

# 1. Хардуерен слой

Най-долният слой: **кой пин към какво е свързан** и **как говорим с ESP-IDF**. Тук няма протокол и логика. Останалият код вика само функциите от `agro_hal.h`, затова логиката се тества на PC без платка.

## 1.1 `components/agro_board/CMakeLists.txt`

| Код | Какво прави |
|---|---|
| `# Заглавният файл board_pins.h включва ...` | Коментар в CMake започва с `#`. |
| `idf_component_register(` | Основната команда на ESP-IDF. Казва: "тази папка е компонент". |
| `INCLUDE_DIRS "include"` | Папката `include` е публична. Всеки компонент, който зависи от този, може да пише `#include "board_pins.h"`. |
| `REQUIRES esp_driver_spi esp_driver_gpio` | Ползва SPI и GPIO драйверите на IDF. Затова `board_pins.h` може да включи `driver/spi_master.h`. |

Няма `SRCS`, защото компонентът е само един заглавен файл. Заглавните файлове не се компилират сами, а се "вмъкват" там, където се включат.

|---|---|---|

## 1.7 Концепции

### Какво е `esp_pm_config_t cfg`

Обикновена структура (`struct`) от ESP-IDF, **не глобална**. Така работят почти всички настройки в IDF:

```cpp
esp_pm_config_t cfg = {};        // нова структура, всички полета = 0
cfg.max_freq_mhz = 80;           // попълваш полетата
cfg.min_freq_mhz = 40;
cfg.light_sleep_enable = true;
esp_pm_configure(&cfg);          // подаваш АДРЕСА ѝ на IDF
```

IDF чете стойностите и ги **копира** в собствената си вътрешна конфигурация. Затова `cfg` може да е локална и да изчезне след функцията. Глобално е само състоянието вътре в IDF. Същият модел има в `gpio_config_t`, `esp_task_wdt_config_t`, `esp_timer_create_args_t`, `MqttLinkConfig`. `= {}` е важно: нулира полетата, които не си попълнил.

### Къде се викат функциите за сън

| Функция | Къде | Кой |
|---|---|---|
| `power_enable_auto_light_sleep(LORA_DIO1)` | `apps/executor/main/app_main.cpp:47` | executor |
| `power_enable_auto_light_sleep(LORA_DIO1)` | `apps/repeater/main/app_main.cpp:37` | repeater |
| `power_deep_sleep_us(SLEEP_US)` | `apps/sensor/main/app_main.cpp:41` | sensor |

Gateway, executor_wifi и config не ги викат. Само sensor-ът има **дълбок** сън. Executor и repeater имат само **лек** сън, и радио модулът им **не** заспива, а слуша непрекъснато (`radio_listen`).

### Как работи автоматичният лек сън

В кода **няма ред "заспивай"**. Сънят се случва като страничен ефект:

1. FreeRTOS винаги има **idle задача** с най-нисък приоритет. Тя върви, когато всички твои задачи чакат (`ulTaskNotifyTake`, `xQueueReceive`, `vTaskDelay`).
2. С включени `CONFIG_PM_ENABLE` и `CONFIG_FREERTOS_USE_TICKLESS_IDLE` idle задачата пита колко тика остават до най-близкото събитие.
3. Ако е достатъчно далече, ESP-IDF (компонентът `esp_pm`, функцията `vApplicationSleep`) спира тик-прекъсването, настройва таймер и пуска чипа в лек сън. FreeRTOS дава кукичката, ESP-IDF прави самия сън.
4. Събужда го DIO1 (HIGH) или таймерът за най-близкия таймаут.
5. След събуждане времето, прекарано в сън, се добавя към тик брояча и към `esp_timer`. Затова `hal_millis()` върви правилно.

В твоя код са само: разрешението (`power_enable_auto_light_sleep`, веднъж), `irqIsr` (когато дойде прекъсване) и цикълът на задачите, който блокира в `ulTaskNotifyTake`. **Чипът заспива само ако всичко чака.** Задача, която върти `while` или вика `vTaskDelay(1)` на кратки интервали, не го оставя да заспи.

## 2.6 `crypto_common.cpp`

### `buildNonce` (ред 8–17)

**Nonce** е 16-байтово число, което прави всяко шифроване различно, дори данните да са същите.

| Байт | Съдържание |
|---|---|
| 0 | типът пакет |
| 1–6 | ID на подателя |
| 7–10 | брояч (big-endian: най-старият байт първи) |
| 11–15 | нули |

| Код | Обяснение |
|---|---|
| `memset(nonce16, 0, 16);` | Нулира 16-те байта. |
| `memcpy(nonce16 + 1, senderId6, CRYPTO_ID_LEN);` | Копира 6 байта от позиция 1 (указателна аритметика). |
| `nonce16[7] = (uint8_t)(counter >> 24);` | Взема най-горния байт на брояча: измества 24 бита надясно. Следват `>> 16`, `>> 8` и без изместване. Съкращаването към `uint8_t` отрязва горните битове. |

### `ctrCrypt`: AES-128 в режим CTR

CTR превръща блоковия шифър в потоков: шифрира поредица от броячи и XOR-ва резултата с данните. Шифроването и дешифрирането са **една и съща операция**.

| Код | Обяснение |
|---|---|
| `mbedtls_aes_context ctx; mbedtls_aes_init(&ctx);` | Състояние на шифъра. |
| `mbedtls_aes_setkey_enc(&ctx, key16, 128) == 0` | Задава ключа (128 бита). 0 е успех. |
| `memcpy(counter, nonce16, 16);` | Началният брой е nonce-ът. |
| `mbedtls_aes_crypt_ctr(&ctx, len, &ncOff, counter, streamBlock, in, out)` | Шифрира `len` байта. На ESP32-S3 ползва **хардуерния AES ускорител**. |
| `mbedtls_aes_free(&ctx);` | Почиства. Винаги се изпълнява. |

Броячът на режима CTR се увеличава в последния байт (15). Нулите в байтове 11–15 са място за блокове, а данните са ≤ 50 байта (4 блока), така че броячът от пакета (байтове 7–10) не се докосва.

### `computeTag`: подписът (CMAC)

| Код | Обяснение |
|---|---|
| `uint8_t macIn[16 + CRYPTO_MAX_PT];` | Буфер: nonce плюс данни, най-много 66 байта. |

| `mbedtls_cipher_cmac(info, key16, 128, macIn, 16 + dataLen, fullMac)` | Изчислява CMAC. Ключът е в **битове**. Нужно е `CONFIG_MBEDTLS_CMAC_C=y`. |

> **Бележка за сигурността:** 4-байтов подпис е компромис за по-кратък пакет. Шансът за налучкване е около 1 към 4 милиарда на опит. Подходящо е за такава система, но е по-слабо от стандартните 8–16 байта.

| Код | Обяснение |

## 2.7 `ceiling_counter.h` и `ceiling_counter.cpp`

**Проблемът:** nonce-ът включва брояч. Ако устройство се рестартира и започне от нула, ще повтори (ключ, nonce), а повторението под CTR разкрива данни. **Решението:** пазиш в NVS "таван" и никога не се връщаш под него. Не се пише във флаша на всеки пакет (флашът се износва), а на всеки 100.

| Код | Обяснение |
|---|---|
| `CEILING_COMMIT_INTERVAL 100UL` | Таванът се вдига на стъпки по 100. |
| `const char *key; uint32_t current; uint32_t committed;` | `current` е следващата стойност, `committed` е записаният таван. |
| `RTC_DATA_ATTR static uint32_t rtcMagic, rtcCurrent, rtcCommitted;` | Променливи в **RTC паметта**, която оцелява при **дълбок сън**, но не при изключване на тока. |
| `if (hal_woke_from_deep_sleep() && rtcMagic == CEIL_RTC_MAGIC) {` | Събуждане от сън **и** паметта е валидна → продължава от RTC без достъп до флаша. |
| `NvsStore s; stored = s.getU32(key, 0); current = committed = stored;` | Иначе започва от тавана. При нечист рестарт броячът скача напред най-много с 100 и никога назад. |
| `if (current >= committed) { newCeiling = current + 100; ... }` | Достигнат е тавана. |
| `if (!s.open(...) \|\| !s.setU32(key, newCeiling) \|\| !s.commit()) { ESP_LOGE(...); return false; }` | Ако **която и да е** стъпка се провали, отказва. По-добре да се пропусне пакет, отколкото да се повтори nonce. |
| `*out = current; current++;` | Връща стойността и увеличава. |
| `rtcMagic = CEIL_RTC_MAGIC; rtcCurrent = current; rtcCommitted = committed;` | Копира в RTC за следващия дълбок сън. |

Класът не е безопасен за много задачи. Вика се само от една задача.

# 3. Радио слой

Тук е всичко, което решава **кога** се предава и как се говори с радио чипа. `radio_timing` и `channel_access` са чиста логика без IDF (затова се тестват на PC). `agro_radio` е единственият файл, който докосва RadioLib.

Три думи от LoRa:

* **Spreading factor (SF 7–12)** е "бавността" на модулацията. По-голям SF значи по-далече, но по-бавно.
* **Bandwidth (BW)** е ширината на канала: 62,5, 125 или 250 kHz.
* **Символ (Ts)** е един "знак" в ефира. Ts = 2^SF / BW. При SF7 и 125 kHz е 1,024 ms, а при SF12 и 125 kHz е 32,8 ms.

## 3.3 `channel_access.h`: правилата за "слушай, преди да говориш"

| Политика | Кой я ползва | Поведение |
|---|---|---|
| **COMMAND** | команди, ACK, state request/response | Първи CAD веднага. Зает → сондиране на всяка стъпка до срока (ToA на най-дългия пакет). Щом се освободи → случаен backoff 0–3 слота → последен CAD. Срокът изтече → `GIVEUP`. |

| **TELEMETRY_FORCE** | heartbeat | Първи CAD. Зает → едно случайно изчакване → втори CAD. Пак зает → предава. |
| **TELEMETRY_SKIP** | heartbeat | Същото, но при втори зает канал се отказва до следващия път. |

## 3.4 `channel_access.cpp`

| Ред | Код | Обяснение |
|---|---|---|
| 3–6 | `CH_ST_FIRST_CAD 0`, `SENSING 1`, `BACKOFF 2`, `TELE_WAIT 3` | Четирите състояния. |
| 8 | `CH_BACKOFF_SLOTS 4` | Случаен backoff 0–3 слота. |
| 11–13 | `static inline bool reached(now, t) { return (int32_t)(now - t) >= 0; }` | "Стигнато ли е времето `t`?" Сравнение със знак, безопасно при препълване на 32-битовия брояч. Просто `now >= t` би се счупило. |
| 22 | `uint8_t channelAccessPoll(...) { switch (ca->state) {` | Автоматът: в зависимост от състоянието прави различно. |

**`FIRST_CAD`** (ред 25–35):

| Код | Обяснение |
|---|---|
| `if (!busy()) return CH_CLEAR;` | Свободно → предавай веднага. |
| `deadline = now + radioSensingWindowMs(); nextAt = now + radioCadStepMs(); state = SENSING;` | Командите и persist телеметрията сондират. |
| `nextAt = now + rnd(radioTelemetryWaitMs() + 1); state = TELE_WAIT;` | Heartbeat политиките: случайно изчакване от 0 до ToA(30 B). |

**`TELE_WAIT`:** времето не е дошло → `WAIT`. Иначе втори CAD. Свободно → `CLEAR`. Зает → `FORCE` предава, `SKIP` се отказва.

**`SENSING`:**

| Код | Обяснение |
|---|---|
| `if (reached(now, deadline)) return PERSIST ? CH_CLEAR : CH_GIVEUP;` | Срокът изтече. Проверява се **първо**. Persist предава въпреки заетия канал, останалите се отказват. |
| `if (!reached(now, nextAt)) return CH_WAIT;` | Още не е време за проверка. |
| `if (busy()) { nextAt = now + step; return CH_WAIT; }` | Още е зает. |
| `nextAt = now + rnd(4) * radioSlotMs(); state = BACKOFF;` | Освободи се. Случаен слот 0–3. Различните устройства рядко започват едновременно. |

**`BACKOFF`:** чака края на слота, после последен CAD. Свободно → `CLEAR`. Зает → обратно в `SENSING` със **същия срок** (не се нулира).

**`channelAccessNextMs`:** в `SENSING` се събужда на по-ранното от следващата проверка и срока. В `BACKOFF`/`TELE_WAIT` е `nextAt`. В `FIRST_CAD` е 0.

**Пример** (команда, SF7, канал зает 119 ms): CAD сочи зает → срок = t+119, проверка на t+11. На всеки 11 ms пита пак. На t+55 каналът е свободен → backoff, пример 2 слота = 22 ms. На t+77 последен CAD. Свободно → предава.

# 4. JSON и конфигурация

Пътят, по който **настройките стигат до устройството**: Python програмата праща ред по серийния порт, приложението `config` го проверява и го записва в NVS, а реалното приложение после само чете NVS. Gateway-ът и Wi-Fi executor-ът ползват JSON и за MQTT.

## 4.1 `json_util.h`: тънък слой над cJSON

**cJSON** е готова библиотека, която превръща JSON текст в дърво от обекти в паметта и обратно. Моят слой добавя само правилата, които проектът изисква.

| Проблем | Какво прави слоят |
|---|---|
| cJSON приема и текст с боклук отзад (`{"a":1} xyz`) | Отхвърля всичко, което не е **точно един обект** |
| cJSON е рекурсивна, а стековете на задачите са малки. Злонамерено съобщение с хиляди `[[[[` би я счупило | Брои вложеността **преди** разбора и отхвърля над 8 нива |
| Твърде дълъг низ би бил отрязан тихо. Отрязан ID на модул може да съвпадне с друг модул | Различава "липсва" от "твърде дълго" и **не реже** |
| cJSON заделя памет. Лесно се забравя да се освободи | Деструкторът освобождава автоматично |

| 289–303 | същото за заявката за състояние | Накрая публикува `{"id":..,"status":"timeout"}`. |
| 305–314 | heartbeat | На всеки 30 s, ако MQTT е свързан. |

В тика **няма блокиране**: нито `delay`, нито чакане. Всичко е сравнения на времена.

### `gw_logic_next_wait_ms` и `gw_logic_task`

| Код | Обяснение |
|---|---|
| `uint32_t best = 5000; auto consider = [&](uint32_t at) { ... };` | Ламбда функция: взема най-близкия срок. `[&]` значи, че вижда локалните променливи. |
| `esp_task_wdt_add(nullptr);` | Абонира се за watchdog. |
| `for (;;) { w = gw_logic_next_wait_ms(); if (xQueueReceive(s_gwInQ, &m, pdMS_TO_TICKS(w)) == pdTRUE) gw_logic_handle(m); gw_logic_tick(); esp_task_wdt_reset(); }` | Чака съобщение най-много до следващия срок, обработва го, проверява таймаутите, храни watchdog-а. **Задачата спи, когато няма работа.** |

### Сценарий: команда, ACK се губи веднъж (SF7)

```
t=0       MQTT "commands" {"M_ID":"E007","C_ID":"V01","com":"A1"} → gw_cmd → startCommand → пакет в radioInQ
t≈0…70    gw_radio: CAD → предаване (62 ms във въздуха)
t≈560     executor: ACK (след 500 ms пауза) ... ACK се загубва
t≈1170    tick: изтекъл radioAckTimeoutCmdMs() (~1,17 s) → retries=1, нов пакет със следващ брояч
t≈1230    executor получава пак; пинът вече е ON → изпълнява "включи" (без промяна) → ACK след 500 ms
t≈1800    gateway получава ACK → handleAck: съвпада → commands_status status=0 → pending=false
```

Ако executor-ът изобщо не отговаря: три изпращания (t=0, 1,17 s, 2,34 s) и при t≈3,5 s `STATUS_TIMEOUT`. През това време всяка нова команда от MQTT се игнорира без отговор.

## 6.5 sensor: общ поглед

Най-простото устройство: **събуждане → измерване → предаване → дълбок сън**. Няма задачи и опашки.

```
събуждане от дълбок сън → app_main започва отначало
  ├─ sensor_tx_reset() и hal_nvs_init()
  ├─ sensor_config_load()           ← NVS (id, честота, SF, ключ, мощност)
  ├─ sensors_init() → sensors_read() → sensors_deinit()   ← I²C, 2 × SHT31
  ├─ sensor_radio_init()            ← RadioLib: reset + begin + настройка
  ├─ sensor_send_packet():
  │     брояч (RTC/NVS) → jitter → криптиране → CAD/достъп до канала → предаване → radio.sleep()
  └─ power_deep_sleep_us(904 s)     ← край, чипът се изключва
```

`app_main.cpp`: `SLEEP_CYCLES 113` × 8 s = 904 s (~15 минути). `power_deep_sleep_us(SLEEP_US)` е последният ред. Нищо след него не се изпълнява.

# 7. Repeater и executor

Двете радио устройства, които спят леко и слушат непрекъснато. Решават един и същ проблем (един радио чип, много задачи) по два различни начина.

| | **Repeater** | **Executor** |
|---|---|---|
| Какво прави | Препраща пакети от една честота на друга | Приема команди, включва/изключва пинове, потвърждава |
| Задачи | `rep_rx` (приоритет 6) и `rep_fwd` (5) | `exec_radio` (6) и `exec_cmd` (5) |
| Защита на радиото | **Mutex** (две задачи пипат радиото) | **Един собственик** (само `exec_radio` пипа радиото) |
| Честоти | Две: приема на едната, предава на другата | Една |

## 7.1 Repeater

### Защо две честоти?

Repeater-ът слуша на **RX честотата** (по подразбиране 434 MHz) и препраща пакета **байт по байт непроменен** на **TX честотата** (по подразбиране 433 MHz, по-близо до gateway-а). Не слага маркер "вече препратен". Цикъл е физически невъзможен, защото всеки хоп е на друга лента. Препратеният пакет е идентичен с оригинала, така че `DedupRing` на gateway-а го познава.

**Защо mutex-ът е правилно направен:**

* Държи се **само по време на реална работа с радиото** (CAD, смяна на честота, предаване). Чакането между проверките е извън него.
* Няма вложени mutex-и, значи няма deadlock.
* FreeRTOS mutex-ът поддържа **наследяване на приоритет**: ако `rep_rx` (6) чака mutex-а, който държи `rep_fwd` (5), `rep_fwd` временно получава приоритет 6 и приключва по-бързо.

**Сценарий:** два repeater-а чуват един и същ пакет.

```
sensor предава на честота A
repeater1 и repeater2 го чуват → и двамата dedup: нов → опашка (sendAt = t + 0..50 ms)
repeater1 (sendAt по-рано): CAD на честота B → свободно → предава → обратно на A
repeater2: CAD на честота B → зает (чува repeater1) → SENSING → изчаква края (до ToA) → backoff слот → CAD → предава
gateway чува две идентични копия → първото минава, второто е дубликат (DedupRing на gateway-а)
```

Опашката е само 4 елемента, а `rep_fwd` обслужва по един кадър наведнъж. При залп от повече от 4 пакета, докато един се препраща (при SF12 може да отнеме секунди), останалите се губят. При нормално натоварване (един sensor на 15 минути) това няма да се случва.

## 7.3 `exec_radio.cpp` (408 реда): подробно

### Какъв проблем решава

Executor-ът трябва едновременно да: слуша за команди, праща ACK 500 ms **след** командата, праща heartbeat на ~5 минути, праща състояние при рестарт и повтаря, ако няма отговор, и да спи, когато няма работа. Всичко става в **една задача**, без блокиращи `delay` в средата. Всяка работа е малка стъпка, която или върши нещо веднага, или казва "не още". ### Сценарий: команда от край до край

```
t=0 ms     gateway предава команда → executor DIO1 HIGH → ISR → радио задачата се събужда
t=0        service(): rxDrain → rxHandle → target ✓ → подпис ✓ → CommandPacket → cmdQ
t=0        exec_cmd (приоритет 5) се събужда: включва пина, AckReq{sendAt = t+500} → ackInQ, xTaskNotifyGive(radio)
t≈1        радио задачата: drainAckIn → acks[0]; ackManager: sendAt не е дошло; nextWaitMs → 499 ms
t=1…499    ulTaskNotifyTake(499 ms): чипът може да заспи леко (DIO1 или таймаут го буди)
t=500      service(): ackManager: ACK е време → построява пакет → txRequest(TXK_ACK, COMMAND)
t=500      radioTxTick: CAD → свободно → radio_transmit → radio_listen → txPending=false
t=500+ToA  gateway получава ACK → публикува commands_status
```

### Сценарий: рестарт

```
boot       consumers_init (всичко OFF) → exec_radio_task → radio_setup → request_restart_response
           sendStateResponseWire(RESTART) → TX слот → предадено (опит 1)
+timeout   няма ACK → restartRespManager: опит 2 (retries=1) → опит 3 (retries=2)
+timeout   няма ACK → отказва се мълчаливо
(ако gateway отговори навреме: rxHandle → STATE_RESP_ACK → restartPending=false)
```

## 7.4 Mutex срещу един собственик

В repeater-а две задачи пипат радиото. Затова има mutex и всяка стъпка го взима и освобождава. Между проверките на канала mutex-ът се освобождава, за да може `rep_rx` да приема.

В executor-а и gateway-а има **един собственик**: само една задача пипа радиото и всичко останало ѝ говори през опашки. Така няма гонка и не трябва mutex. Това е препоръчаният стил във FreeRTOS, а repeater-ът е по-стар дизайн.

## 7.5 Бележки за сигурност и ограничения

1. **Няма защита от повторно възпроизвеждане (replay).** Executor-ът проверява подписа, но не следи броячите на получените команди. Записана валидна команда "включи", излъчена повторно, ще се изпълни. `CeilingCounter` пази само подателя от повтаряне на nonce, не защитава получателя.
2. **Repeater-ът не проверява подписа.** Препраща всичко с вярна CRC. Gateway-ът отхвърля фалшивото накрая.
3. **Без watchdog.** Мъртъв радио чип на repeater или executor оставя устройството в цикъл на опити. Това е по твое желание.

Executor без LoRa. Получава командите **директно по MQTT през Wi-Fi**, превключва същите пинове и отговаря със същите теми и JSON като LoRa пътя. ## 9.2 Какво е намерено и поправено

| № | Проблем | Поправка |
|---|---|---|
| 1 | `CONFIG_MBEDTLS_CMAC_C` е **изключен по подразбиране**, а `executor_wifi` и `config` компилират `crypto_common.cpp` (през `agro_core`). Билдът им щеше да се счупи. | Добавена е опцията в двата `sdkconfig.defaults`. |
| 2 | Task Watchdog е включен по подразбиране в IDF (5 s, само предупреждение) и в петте приложения, за които не е искан watchdog. | `CONFIG_ESP_TASK_WDT_INIT=n` в `sensor`, `executor`, `repeater`, `executor_wifi`, `config`. README е обновен. |
| 3 | `if (woken) portYIELD_FROM_ISR();` работеше, но не в стандартния вид. | `portYIELD_FROM_ISR(woken);` в `hal.cpp:61`. |
| 4 | Остарял коментар в `agro_radio.h:15` (`hal.h`). | Поправен на `agro_hal.h`. |

## 9.3 Какво не е потвърдено

* **Минимална честота 40 MHz при максимум 80 MHz** на ESP32-S3. Документацията не дава допустими стойности. Ако не е валидно, `esp_pm_configure` връща грешка и кодът я логва.
* **Тялото на `gpio_ll_intr_disable`.** От наличния код не се вижда да пипа настройката за събуждане. Събуждането от DIO1 трябва да се пробва на платка.
* **Колко ток харчи Task WDT в лек сън.** Затова е изключен там.
* **`esp_random()` е псевдослучаен без включено Wi-Fi.** Документацията го казва. Ползва се само за jitter и изчакване, не за ключове и nonce.
* **Поведението на `getchar()`** в приложението `config` (UART или USB Serial/JTAG конзола).
* Част от проверките минаха през инструмент, който преразказва страниците, а не ги цитира дословно. Версиите на `esp-mqtt` и mbedTLS в IDF 5.3 и 5.5 може да се различават леко.

Истинската проверка остава **`idf.py build`** с ESP-IDF 5.3–5.5, а после проба на платка.

## 9.4 Излишни неща

* Четири функции се ползват само от тестовете, не от прошивката: `hal_delay_us`, `hal_micros`, `mqtt_link_down_ms`, `wifi_link_down_ms`.
* `CONFIG_FREERTOS_IDLE_TIME_BEFORE_SLEEP=3` е равно на стойността по подразбиране.
* Task WDT на gateway е зададен два пъти, и в `sdkconfig`, и в кода. Това е нарочно.
* В `agro_net/CMakeLists.txt` е изброена зависимост от `agro_core`, която кодът не ползва.

## 10.2 Устройствата и пътят на пакетите

```
                    f1                  f2
  sensor ───────────22 B────► repeater ───22 B────┐
  (2 × SHT31)                                      ▼
                                              ┌─────────┐   MQTT    ┌──────────┐   MQTT   ┌─────────────┐
                                              │ gateway │◄─────────►│  MQTT    │◄────────►│   Сървър    │
                                              │         │           │  брокер  │          │ бекенд+табло│
                                              └────┬────┘           └────┬─────┘          └─────────────┘
                                         команда   │  ▲  ACK             │ wifi_commands
                                          26 B     ▼  │  20 B           ▼
                                              ┌─────────┐          ┌───────────────┐
                                              │executor │          │ executor_wifi │
                                              └────┬────┘          └───────┬───────┘
                                                   ▼ GPIO                  ▼ GPIO
                                             консуматори              консуматори
```

Три отделни пътя:

1. **Измерване (нагоре).** `sensor` се събужда, чете двата SHT31, праща 22-байтов криптиран пакет по LoRa и заспива за 15 минути. Ако sensor-ът е на честотата на gateway-а, gateway-ът го чува директно. Иначе го чува `repeater` на честота f1 и го препраща **непроменен** на f2. `gateway` проверява подписа, маха дубликатите и публикува в MQTT тема `sensors`.
2. **Команда (надолу) и потвърждение.** Сървърът публикува в `commands`. `gateway` предава 26-байтова команда по LoRa, `executor` я изпълнява и 500 ms по-късно праща 20-байтов ACK. `gateway` публикува `commands_status`. Repeater-ът **не** препраща команди и ACK-ове.
3. **Wi-Fi executor.** `executor_wifi` е същото като `executor`, но говори **директно с брокера** на тема `wifi_commands`, без LoRa и без gateway. Сървърът не усеща разликата, защото темите за отговор са същите.

Отделно от тях е **конфигурацията**: Python програмата → серийният порт → приложението `config` → NVS. Тя не участва в нормалната работа.

## 10.5 Осем принципа, на които стои системата

1. **Слоеве.** Логиката (протокол, времена, автомат за канала) не знае за ESP-IDF. Говори само с `agro_hal`. Затова 264 теста вървят на PC.
2. **Един собственик на радиото.** Gateway-ът и executor-ът имат по една задача, която пипа радиото, а останалите ѝ пращат заявки по опашки. Repeater-ът има две задачи и mutex.
3. **Опашки, не споделени променливи.** Всичко между задачи и ядра минава през `xQueueSend` и `xQueueReceive`. Прекъсването (ISR) само буди задачата.
4. **Неблокиращи автомати.** Всяка работа е малка стъпка, която казва "готово" или "още не". Накрая задачата изчислява `next wait` и блокира точно толкова. Така процесорът не върти на празно и чипът може да заспи.
5. **Времената са изчислени.** CAD, ACK таймаути и ширини на прозорци идват от SF и ширина на канала, нищо не е хардкоднато в милисекунди.
6. **Безопасни подразбирания.** При старт консуматорите са изключени. Липсва ключ или ID → не предава. Провал на запис в NVS → не излъчва с непотвърден брояч. Непознат пин → не се пипа.
7. **Подпис преди доверие.** Проверява се целта (евтино), после MAC, и чак тогава се действа. Броячът на nonce се пази с таван във флаша.
8. **Конфигурацията е отделна.** Само приложението `config` пише в NVS. Всички останали само четат при старт.
